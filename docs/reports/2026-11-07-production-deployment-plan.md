# AegisAI 실배포 준비 및 운영 검증 계획

> 최초 작성은 2026-11-07이다. 2026-11-09 사용자 지시로 Blue/Green·Canary·Kubernetes RollingUpdate·HPA를 확장 마일스톤의 필수 조건으로 상향했다.
> 같은 날 후속 지시로 IaC·GitOps/CD·공급망 보안·로그/메트릭/트레이싱(H1~H4)도 필수로 복원했다. G와 H의 여덟 항목 모두 실제 구현·검증이 필요하다.
> 과거 상태 표는 작성 당시 기록이며, 최신 상태와 남은 작업은 이 문서의 9절 및 [남은 작업](../production/remaining-work.md)을 따른다.

작성일: 2026-11-07 KST

## 1. 목적과 적용 범위

기존 AWS EC2와 Tailscale을 활용해 AegisAI를 실제 사용 가능한 서비스로 배포한다.
서버가 실행되는 것과 실제 저장소를 안전하게 분석하는 서비스가 완성된 것을 구분한다.
동시에 클라우드·DevOps·인프라 포트폴리오에 사용할 구현 및 운영 증거를 확보한다.

첫 출시 범위는 GitHub Cloud와 결정론적 Java 스캔이다. GitLab과 AI 추론은 후속 범위로
유지한다. AI를 도입하더라도 조언만 제공하며, 확정 취약점이나 정책 판단을 대신하지 않는다.

이 문서는 대화에서 정한 계획을 정리한 문서다. 실행 기준은 아래 명세를 따르며,
이 문서 작성 자체가 작업 완료나 추가 인프라 생성·비용 승인을 의미하지 않는다.

## 2. 현재까지 확인된 상태

아래는 기존 배포 기록과 로컬 명세를 기준으로 정리한 상태다.
이 문서 작성 중 서버 상태를 새로 조회하거나 배포를 실행하지 않았다.

| 항목 | 기록된 상태 | 남은 검증 |
| --- | --- | --- |
| AWS 접속 | 기존 EC2 및 Tailscale 사설 HTTPS 구성 | 운영 접근 정책·키 만료 관리 |
| 실행 환경 | API·웹·PostgreSQL·Redis 배포 및 상태 확인 | 전체 운영 승인 조건 충족 |
| 데이터 영속성 | 사용자·테넌트·연동·저장소·스캔 요청 DB 저장 | 새 큐 기능과의 통합 회귀 검증 |
| 기존 후보 검증 | 기본 테스트 130개, 이미지 내 App 테스트 16개, DB 테스트 8개 통과 기록 | 이후 변경에 대한 재검증 |
| OAuth | 기존 GitHub 설정을 AWS 주소에 반영하고 리다이렉트·PKCE·쿠키 확인 | 제공자 콜백 등록 및 실제 로그인 완료 |
| GitHub App | 개인 설치 소유권·선택 저장소 메타데이터 검증 구현 | 실제 App 키·설치를 연결한 검증 |
| 작업 큐 | DB 모델·마이그레이션·서비스 구현 진행 중 | 실제 DB 통합 테스트·마이그레이션·배포 검증 |
| 실제 스캔 | 격리 실행·실제 분석기 연결 미완료 | 전체 Scan Plane 구현 및 검증 |
| 백업·복구 | 초기 DB 복원·API 재시작 확인 기록 | 실제 데이터 규모의 복구·롤백 검증 |
| 서비스 진입점 | 사설 HTTPS에서 유지보수 상태, 준비 상태 false | 모든 출시 조건 통과 후 전환 |

작업 큐 구현은 중간 상태다. 스키마 검증이나 타입 검사만으로 DB 동시성·복구가
검증된 것으로 표시하지 않는다. 기존 테스트 통과 수를 새 변경의 검증 결과로 재사용하지 않는다.

## 3. 유지할 보안·제품 원칙

- 사용자 로그인 OAuth와 저장소 접근용 GitHub App 자격증명을 분리한다.
- 테넌트는 로그인 세션에서 결정하며, 요청 본문의 테넌트 값을 신뢰하지 않는다.
- Control Plane, Scan Plane, AI Plane, Data/Security Plane 경계를 유지한다.
- 스캔은 별도의 일회성 VM 또는 명세를 충족하는 샌드박스에서 실행한다.
- 고객 코드를 실행하거나 고객 저장소의 패키지를 설치·빌드하지 않는다.
- 소스 직접 업로드 기능을 추가하지 않는다.
- 토큰·서명 키·비밀 값은 로그, 소스, 이미지, 보고서에 포함하지 않는다.
- 모의 결과를 실제 분석 결과로 노출하지 않는다.
- 공유 API 계약은 `packages/shared`에 둔다.
- 세션·CSRF·요청 제한·상태 확인·핵심 통합 테스트를 유지한다.

## 4. 실행 순서와 단계별 완료 기준

### 단계 A. 작업 큐와 트랜잭션 검증

1. 스캔 요청과 큐 작업을 같은 DB 트랜잭션으로 저장한다.
2. 동일한 canonical scan request는 동일한 작업을 재사용한다.
3. 기존 요청 이관은 QUEUED·PLANNING에 한정한다. 완료·실패·취소 작업을 재실행하지 않는다.
4. DB 시간을 기준으로 60초 임대와 시도별 fencing token을 사용한다.
5. 작업 선점은 전체 2개·테넌트별 1개로 제한한다. 이는 디스패치 임대 한도이며,
   실제 VM 수나 전체 서비스 처리량을 보장하는 수치로 표현하지 않는다.
6. 재시도는 지수 백오프와 최대 5회 제한을 적용한다. 초과 시 작업을 DEAD,
   스캔을 FAILED로 전환하고 감사 기록을 남긴다.
7. 연동 해제 시 대기·임대 작업을 원자적으로 취소한다. 정지 테넌트와 해제된 연동의
   작업은 새로 선점하거나 완료 처리할 수 없어야 한다.

완료 증거는 전용 PostgreSQL에서의 생성 실패 롤백, 동시 중복 요청, 동시 선점,
용량 제한, 임대 만료 후 이전 작업자 응답 거부, 백오프, 재시도 소진, 테넌트 격리,
연동 해제, 별도 프로세스 재접속 테스트다.

큐는 at-least-once 전달을 전제로 한다. 임대만으로 exactly-once 스캐너 실행을
보장하지 않는다. 실제 소비자를 연결하기 전에는 scan ID 기반 프로비저닝 멱등성,
이전 샌드박스 정리·대조, 영속적인 인계 완료 시점을 구현한다.
디스패치 완료를 스캔 완료로 처리하지 않는다.

### 단계 B. 실제 인증·저장소 연동

1. AWS의 최종 HTTPS 주소와 GitHub 제공자 콜백 설정을 맞춘다.
2. 실제 사용자 로그인, 세션 유지·로그아웃, CSRF 및 인증 실패 처리를 확인한다.
3. 실제 GitHub App ID·서명 키·설치를 연결한다. 초기 범위는 개인 소유 설치다.
4. 설치 소유권, 허용 저장소, 연동 해제·정지 상태를 제공자 응답으로 확인한다.
5. 스캔 대상 브랜치·태그를 제공자가 확인한 고정 commit SHA로 해석한다.
6. 저장소·스캔 단위로 범위를 제한하는 토큰 브로커를 구현한다.
7. 스캔 자격증명은 명세의 최대 10분 수명과 회수·실패 처리를 충족해야 한다.

메타데이터 조회 후 즉시 폐기하는 현재 discovery 토큰을 스캔 자격증명 구현으로
간주하지 않는다. 조직 설치는 조직 권한 검증이 준비되기 전까지 허용하지 않는다.

### 단계 C. AWS 권한과 격리 실행 환경

1. 사용할 AWS 계정·리전·인증 주체와 기존 자원을 확인한다.
2. 격리 스캔에 필요한 IAM, 네트워크, 이미지, 저장소, 로그 권한을 구체화한다.
3. 예산 상한·동시 실행 한도·자동 종료·잔여 자원 정리·중지 절차를 정한다.
4. Control Plane과 분리된 일회성 실행 환경을 구성한다.
5. 테넌트 간 접근, 불필요한 외부 통신, 메타데이터·비밀 접근을 제한한다.
6. 타임아웃·작업자 종료·프로비저닝 실패 때 자원과 자격증명이 회수되는지 확인한다.

현재 EC2에 SSH로 접근할 수 있다는 사실을 AWS API 권한이나 격리 스캔 환경이
준비된 증거로 사용하지 않는다. 정확한 자원·비용 조건을 정한 후 프로비저닝한다.

### 단계 D. 실제 스캐너와 결과 저장

1. 격리된 환경에서 허용 저장소의 고정 commit만 가져온다.
2. 승인된 Opengrep·Trivy·Syft 실행을 연결하고 도구·규칙 버전을 기록한다.
3. 고객 코드 실행·패키지 설치·빌드 없이 Java 우선 분석을 수행한다.
4. 입력 크기·출력 크기·파일 수·시간·자원 사용량을 제한한다.
5. 결과를 정규화하고 취약점·커버리지·실패 상태를 영속화한다.
6. 큐 재전달과 작업자 장애에도 오래된 결과나 중복 결과가 최종 결과를 덮어쓰지 않게 한다.

완료 기준은 승인된 테스트 저장소를 실제로 분석하고, 저장된 결과가 사용자 API까지
전달되는 것을 확인하는 것이다. 도구 프로세스가 실행된 것만으로 완료 처리하지 않는다.

### 단계 E. 증거·정책·사용자 화면

1. 증거를 테넌트·스캔 범위로 저장하고 암호화·접근 제어·보존 기한·삭제를 검증한다.
2. 결정론적 정책과 필수 커버리지 조건을 적용한다.
3. 실패·부분 분석·취소를 정상 완료와 구분한다.
4. 프런트엔드의 fixture·모의 결과 경로를 실제 구현 API로 교체한다.
5. 로그인 → 설치 연동 → 저장소 선택 → 스캔 요청 → 진행 조회 → 결과 조회를 검증한다.
6. 미지원 GitLab·AI 기능은 사용 불가 상태를 명확히 표시한다.

### 단계 F. 운영 검증과 출시

1. 전체 검증 경로를 다시 실행하고 대상 이미지에서도 핵심 검증을 수행한다.
2. 마이그레이션 전 백업과 전용 DB 복원 검증을 완료한다.
3. 프로세스·서버 재시작, DB·Redis·GitHub 장애, 작업자 장애를 검증한다.
4. 로그·메트릭·알림·감사 이벤트를 연결하고 알림 전달을 확인한다.
5. 실제 데이터·부하를 기준으로 처리량·지연·실패율·복구 시간을 측정한다.
6. 이전 이미지와 DB 스키마 호환성을 확인하고 롤백을 실제로 연습한다.
7. 운영 절차와 접근 정책을 확정한 후 서비스 진입점을 전환한다.
8. 전환 직후 실제 로그인과 실제 스캔을 다시 확인한다.

초기 빈 DB의 복원 시간을 실제 운영 데이터의 RTO로 제시하지 않는다.
이미지 롤백과 DB 롤백을 구분하며, 데이터 볼륨 삭제를 배포·복구 절차로 사용하지 않는다.

### 단계 G. 필수 배포 전략과 자동 확장 — 2026-11-09 추가

| ID | 필수 항목 | 구현 범위와 완료 기준 |
| --- | --- | --- |
| G1 | Blue/Green | 기존·후보 앱 버전을 별도 실행하고 후보의 readiness·DB/세션 호환성을 확인한다. 비공개 진입점 전환과 이전 버전 복귀를 실제 수행한다. 버전별 요청 응답, 오류·지연, 전환/복귀 시간과 원래 버전 보존을 기록한다. |
| G2 | Canary | 버전별 요청 식별과 가중치 라우팅을 구현한다. 10%→50%→100%를 초기 목표로 삼되 요청 수·관측 시간·오류율·p95 기준을 실행 전에 확정한다. 기준 초과 시 자동 중단·기존 버전 복귀를 검증하고 실제 분배 요청 수를 남긴다. 통제된 검증 요청과 실제 사용자 트래픽을 구분한다. |
| G3 | Kubernetes RollingUpdate | 실제 API/웹 워크로드에 readiness/startup, graceful shutdown과 자원 requests/limits를 구성한다. 초기 목표 maxUnavailable=0, maxSurge=1의 수용 가능성을 먼저 확인한다. 정상 교체와 준비 실패 후보의 서비스 제외·운영자/자동화 복귀를 확인한다. Deployment가 자동 롤백한다고 가정하지 않는다. |
| G4 | HPA | 실제 Kubernetes autoscaling/v2와 Metrics API를 연결한다. 우선 API에 minReplicas=1, maxReplicas=2 범위의 수용 가능성을 검토한다. 자원 requests·목표 지표·안정화 정책을 확정하고 제한된 부하에서 1→2→1 자동 증감, 지표 부재 시 동작, 세션·요청·DB/큐 정합성을 확인한다. |

네 항목은 모두 미완료다. 현재 EC2 한 대·추가 컴퓨팅 금지 조건은 유지한다. 먼저 OS·DB·Redis·독립 gVisor 스캐너·Kubernetes 제어 영역·겹치는 앱 인스턴스의 CPU/메모리/디스크 예산을 계산하고 실측한다.
용량이 부족하면 실제 제약으로 차단 상태를 보고하며 추가 EC2/EKS/Fargate나 증설을 임의 수행하지 않는다. 별도 실험 환경 결과만으로 이 필수 조건을 충족한 것으로 낮추지 않는다.

HPA는 Pod 수 조절이며 노드 자동 증설이나 고가용성을 뜻하지 않는다. 실제 무거운 스캔 동시 실행은 계속 한 건이다. DB·Redis·브로커·감독 프로세스를 무분별하게 복제하지 않는다.
스캐너의 root 전용 containerd, UID 경계, 네트워크 차단·자격증명 회수·소스 정리를 보존한다. DB 변경은 구·신 앱 동시 호환이 선행해야 한다.
Kubernetes 운영 전환은 구현 패키지·위협 모델·자원 및 복구 설계를 먼저 정하고 적용되는 005/006 외부 자격/배포 제한을 충족해야 한다. 이번 계획 변경은 해당 게이트 통과나 운영 전환 승인이 아니다.

진행 순서는 **자원/경계 설계 → 관측·알림 → Kubernetes 적용 선행 조건 → RollingUpdate → Blue/Green → Canary → HPA → 통합 복구·비용 확인**이다.
현재 서비스는 유지한다. 문서 수정 지시만으로 클러스터 설치·트래픽 전환·장애 주입·AWS 자원 생성을 수행하지 않는다.

기술 기준: [Kubernetes Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/), [Horizontal Pod Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).

### 단계 H. 누락된 플랫폼 운영 요구 복원 — 2026-11-09 추가

사용자가 초반 계획에서 누락·약화된 상위 네 항목을 추가하도록 지시했다. 아래 H1~H4도 **실제 구현·검증 필수**다. 기존 G1~G4는 그대로 유지하며, 확장 마일스톤은 총 여덟 필수 항목을 모두 충족해야 한다. 이번 추가는 문서 범위이며 서버 변경·자원 생성·권한 확대 승인이 아니다.

| ID | 필수 항목과 목표 기술 | 구현 범위와 완료 기준 |
| --- | --- | --- |

Helm은 구성 패키지, Argo CD는 선언 상태 동기화, Argo Rollouts는 G1/G2 전환, HPA는 replica 조절을 담당하도록 소유권을 명시하고 충돌을 검증한다. AWS 작업에는 저장소·브랜치/환경·대상 자원이 제한된 GitHub OIDC 역할을 사용하고 장기 AWS 키를 새로 배포하지 않는다. G3와 적용되는 Kubernetes 자격/배포 게이트를 우회하지 않는다. |
| H3 | 공급망 보안 — 배포 이미지 검사·SBOM·서명/검증 | 배포할 API/웹 이미지의 digest별 취약점 검사·SBOM·빌드 출처·서명을 생성하고 보존한다. 허용 서명 주체/발급자 또는 키·신뢰 기준, 취약점 차단 기준과 예외 만료를 정한다. 누락·불일치·변조된 서명/산출물과 정책 위반 이미지가 배포 전 실제 거부되는 것을 확인한다. 고객 저장소 대상 Trivy/Syft 실행이나 단순 해시 검증을 배포 이미지 서명 검증으로 대신하지 않는다. |

Oracle 설정의 존재만으로 AWS 적용 완료를 표시하지 않는다. |

H1~H4는 모두 미완료다. 이미 완료한 CI·불변 이미지·해시 검증·상태 확인은 재사용할 기반이며 각 항목 전체의 완료 증거는 아니다. 특정 서명 도구와 레지스트리/backend는 호환성·권한·비용 검토 후 고정한다. 이번 지시로 EKS·RDS·ALB·새 EC2 등 추가 유료 토폴로지를 승인하거나 기존 PostgreSQL 큐를 SQS로 교체하지 않는다.

H4의 Grafana·Loki·Prometheus는 사용자 지정 필수 스택이다. Grafana는 통합 시각화·탐색/알림, Loki는 로그 저장·조회, Prometheus는 메트릭 수집·조회를 담당한다. Grafana에서 Prometheus 지표와 Loki 로그를 실제로 조회하고 동일 요청/스캔의 상관관계를 확인해야 한다. 대시보드나 호환 API 이름만 추가해 세 도구를 모두 사용한 것으로 처리하지 않는다. Grafana의 Cloud/자체 호스팅 배치와 저장 위치는 기존 EC2 한 대·추가 컴퓨팅 금지·자원/비용 조건 안에서 확정한다. 기존 OpenTelemetry 추적 요구는 유지하고 추적 저장 backend는 별도 선정한다. 세 도구의 메트릭·로그 연결만으로 분산 추적까지 완료 처리하지 않는다.

H2의 관리 책임 표에는 Terraform의 클라우드 자원, Helm/Argo CD의 앱 설정, Rollouts의 트래픽 전환, HPA의 replicas를 구분한다. API 트래픽 Canary와 큐 작업/worker 버전 전환은 별개로 설계한다. 스캐너·브로커의 단일 실행 및 기존 격리 경계를 유지하고 구·신 API/worker/DB 계약 호환성을 확인한다.

추가 후 실행 순서는 **자원·관리 책임·예산 설계 → H1 IaC → H4 관측/추적·F-4 알림 → H3 공급망 보안 → Kubernetes 선행 게이트 및 H2 GitOps/CD → G3 RollingUpdate → G1 Blue/Green → G2 Canary → G4 HPA → 통합 장애·복구·비용·사용자 흐름 확인**이다. 자원이나 권한이 부족하면 실제 차단 조건을 보고하며 실습 결과나 문서만으로 필수 항목을 완료 처리하지 않는다.

## 8. 확장 마일스톤 최종 완료 체크리스트

- [ ] 최종 HTTPS 주소에서 실제 GitHub 로그인과 세션 처리가 검증됨.
