# 남은 작업과 적용 범위

현재 비공개 실배포와 전체 제품 명세 완료를 구분한다. 아래 항목은 미구현 기술을 이미 적용한 것처럼 포장하지 않고, 다음 코드 작업을 선택하기 위한 기준이다. 문서화 과정에서는 새 인프라 생성, 비밀 회전, 복구 사본 삭제를 수행하지 않는다.

## 다음 작업 순서

| 우선순위 | 작업 | 완료를 판단할 근거 |
| --- | --- | --- |
| 1 | 변경 범위 검토와 재현 가능한 릴리스 | 기존 사용자 변경을 구분한 커밋·PR, 실제 배포 파일과 커밋의 대응, hosted CI 결과 |
| 2 | 남아 있는 운영 보안 예외 정리 | 비활성 로컬 비밀 사본과 이전 설정의 목록·참조 확인·복구 계획, 승인된 범위의 제거·필요한 회전 기록 |
| 3 | 운영 알림과 보관 정책 보완 | 디스크·서비스·백업·retention 실패를 외부로 전달, 365일 메타데이터·감사 기준에 대한 구현·보존 증거 |
| 4 | 사용자 조작 경로의 최종 확인 | 실제 로그인 후 브라우저 새 요청·결과 조회·근거 다운로드 확인, 필요 이상 새 저장소를 분석하지 않음 |
| 5 | 선택적 AI 연동 | 자체 로컬 모델 또는 임시 API, 축소 근거만 전달, 미설정·실패 시 기본 스캔 유지 |
| 별도 범위 | 일반 서비스 확장 | 별도 노드·서비스별 IAM·공개 intake·다중 테넌트·HA·정량 SLO를 별도 설계하고 검증 |

이미 사용자에게 삭제하지 않겠다고 확인한 이전 EBS 디스크·스냅샷은 보존한다. 로컬 비활성 비밀 사본과는 다른 자산이며 한 번에 일괄 삭제하지 않는다. 추가 EC2·Fargate·NAT Gateway 없이 진행한다는 제약도 계속 유효하다.

우선순위 2에서는 deploy-candidate.sh의 이전 runtime.env 존재 확인도 제거 대상인지 검토한다. 의존성을 먼저 바꾸고 복구가 되는지 확인하기 전에는 파일만 지우지 않는다. 우선순위 3에는 로컬 백업의 자동 보관 제한, 백업 실패 시 오래된 성공 JSON 탐지, 복원 검증 이력의 독립 보존과 실제 전체 복구 절차 수립도 포함한다.

비용 점검도 우선순위 3에 포함한다. 추가 컴퓨팅 없이 발생하는 S3·비밀 보관·KMS·잔여 EBS/스냅샷 비용을 측정하고, 필요하면 사용자 예산에 맞는 경보를 정한다. 현재 월 청구 금액의 강제 상한이나 예산 알림이 구현됐다고 표현하지 않는다.

## 기술 적용 여부

| 기술·기능 | 현재 상태 | 문서에 사용할 표현 |
| --- | --- | --- |
| Compose 컨테이너 교체 | 적용 | 단일 호스트 교체 배포, 짧은 중단 가능 |
| Blue/Green | 미적용 | 트래픽 전환·이전 실행 환경 동시 유지·검증 체계가 필요 |
| Canary | 미적용 | 트래픽 분할·지표 기반 중단·자동 복귀가 필요 |
| Kubernetes RollingUpdate | 미적용 | 현재 Kubernetes 워크로드가 없음 |
| HPA | 미적용 | 수평 확장 제어 없음, 현재 실제 분석 한 건으로 제한 |
| Terraform·Helm·Argo CD | 미적용 | 현재 Python/AWS API·셸·Compose·systemd 운영 자산 사용 |
| GitHub Actions CI | 구성 있음, 해당 배포 hosted 결과 미확인 | 로컬·대상 이미지 검증과 구분 |
| AWS 자동 CD·GitOps | 미구현 | 현재 운영자 실행 배포, Oracle의 기존 CD와 구분 |
| Prometheus·Grafana·외부 알림 | AWS 운영 환경 적용 미확인 | 현재 journald·health·상태 파일·실패 시 차단, Oracle 설정을 AWS 성과로 쓰지 않음 |
| SSE-KMS·Secrets Manager·IAM 역할 | 적용 | 실제 런타임 접근·암호화 근거·부팅 복구 확인 |
| 백업 복원 | 특정 절차 확인 | S3 백업 다운로드·해시·검증 DB 복원, 전체 재해복구 완료 주장 금지 |
| 자동 이미지 롤백 | 웹 실패 시 복귀 코드 있음 | 실제 확인한 접근 차단·복원과 구분, 임의 이전 API 이미지 호환성은 미인증 |
| AI API·자체 모델 | 미연결 | AI DISABLED, 기본 분석 사용 가능 |
| GitLab·웹훅·PR 댓글·PDF·자동 수정 | 현재 운영 범위 밖 | 화면·설계·이전 코드의 존재를 운영 기능으로 제시하지 않음 |

Blue/Green·Canary·HPA를 포트폴리오에 적기 위해 이름만 추가하지 않는다. 현재는 제한된 비용·단일 호스트·격리된 실행과 복구 근거를 설명하는 편이 정확하다. 적용하려면 전환/증감 조건, 관측 지표, 실패 처리와 실제 검증 결과까지 있어야 한다.

## 제품 기준과 남아 있는 차이

- 같은 호스트이므로 별도 control/scan 노드와 고가용성 기준을 충족하지 않는다. gVisor는 공유 호스트 위험을 없애지 않는다.
- 현재 인스턴스 역할은 호스트 신뢰 영역이 공유한다. 컨테이너별 IAM 역할·테넌트별 독립 KMS 키를 적용했다고 표현하지 않는다.
- 근거 7일 만료는 구현했지만 findings·scan metadata 기본 365일 수명주기 전체를 자동화한 상태는 아니다. 감사 기록 최소 365일 유지 및 독립 불변 보관에 대한 운영 증거도 더 필요하다.
- 활성 비밀은 관리형 저장소에서 읽지만 비활성 로컬 사본과 과거 미암호화 복구 사본이 남아 있다. 모든 비밀·모든 사본의 기준 충족을 주장하지 않는다.
- 초기 Java 규칙과 선언된 의존성의 LIMITED coverage다. 전체 Java 취약점, 모든 전이 의존성, 정량 검출률을 보장하지 않는다.
- 상태·로그·주기 작업은 있으나 외부 호출 알림, 부하 기반 정량 SLO, 무중단·자동 수평 확장은 미완료다.

## 포트폴리오 서술 예시

> 단일 EC2 제약 아래 비공개 Java 보안 분석 서비스를 배포했다. GitHub 사용자 인증과 저장소 App 권한을 분리하고, PostgreSQL 작업 큐와 fencing으로 분석 결과를 확정한다. 저장소 소스는 전용 게이트웨이가 가져오며 별도 containerd/gVisor 환경에서 네트워크 없이 고정 분석 도구만 실행한다. S3/KMS 근거 저장, Secrets Manager 기반 부팅, 실제 저장소 분석·소스 정리·백업 복원·재시작 복구를 확인했다. 현재 범위는 단일 사용자·조직이며 AI와 고가용성은 후속 과제다.

개인의 수동 구현과 보조 도구의 기여는 실제 작업 기록을 기준으로 설명한다. 합격률, 무중단, 장애 복구 시간, 성능 개선율 등 측정하거나 입증하지 않은 수치는 쓰지 않는다.
